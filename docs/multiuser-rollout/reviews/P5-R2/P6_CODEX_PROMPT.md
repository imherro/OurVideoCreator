## 1. 第一版完成目标与非目标

在当前React + FastAPI + PostgreSQL + 外部API架构上，形成：

**获权成员提交 → 幂等验证与原子预占 → 两个独立Worker安全领取 → 固定原模型/凭证及对象输入执行 → 明确恢复/未知/取消规则 → 候选或素材幂等归档 → 平台后台查看队列、额度与待核对事项。**

优先把状态和副作用边界做正确，再增加并发。复用已有jobs与Provider模块，可增加必要的attempt、配额、用量/预约或锁记录及Alembic迁移；不要求每一类计数单独做复杂服务。不引入Redis/Celery/Kafka、微服务、Kubernetes、CRDT/OT或全量事件溯源平台。

测试至少支持两个真正独立的Worker进程。可以仍在同机、默认只启动一个Worker；不把两线程等同于两进程，也不把两进程测试当作百人吞吐承诺。

本阶段额度是提交使用限制，不是人民币预算或供应商准确账单。UI/文档不得把估算写成结算。

## 2. 先在实际代码中明确一次执行的边界

先补一份精简的状态/副作用映射，再依此实现，不另起新阶段等批准。最少列：

- 本地排队/已领未发送；准备发起请求；接单状态不明；已有上游ID；远端运行；结果下载/登记；成功/取消/失败/待人工核对。
- 每项允许的前置状态、当前attempt条件、是否可能产生新费用、配额/执行槽/远端在途计数处理、能否安全重试。
- 各现有adapter的提交/查询/取消/幂等能力；上游不支持或未验证就明确写不支持/未验证，不能臆造协议。

可以沿用现有六个公开job.status并用phase/子状态表示细节，也可以作有测试的扩展；不要仅为了名字统一破坏任务页和既有前端。

所有失败出口应提供脱敏、可判定的错误与恢复动作。不要将不明确的提交结果简单归类为普通failed后自动重试。

## 3. 两Worker、租约与旧执行者写入保护

1. 使用PostgreSQL短事务原子领取（SKIP LOCKED或已验证等价机制），持久化worker_id、attempt编号/令牌、lease expiry、heartbeat。I/O和FFmpeg不占用领取事务。
2. P5的“全数据库只许一个Worker”限制必须被可证明正确的任务级领取/租约替代后才允许双Worker。不能只删除排他锁；不得保留启动时把所有running一律改interrupted的行为。
3. Worker启动/恢复只处理符合到期和状态规则的任务，不触碰其他Worker的有效租约。租约时钟使用数据库时间或另一明确一致的服务器时间方案；不要依赖浏览器时间。
4. 心跳、阶段状态、provider handle、结果与候选/最终登记由当前attempt条件保护。受影响行数为0意味着失去资格，应停止后续本地写/新提交，不当作成功。
5. 每个由Worker到达的修改入口都要纳入这一规则，不只在最终status处补条件。不得在adapter内部用无token的store方法绕过。
6. lease到期后旧Worker迟到写不能覆盖新attempt；也不能把fencing写成可以撤回已经发出的网络请求。提交状态不明时采取保守恢复，避免新旧进程都重新发起费用。
7. 保留P1的Web/Worker独立、精确进程所有权和环境恢复。两Worker的测试使用各自明确进程ID；无需重写整套Windows服务管理。默认启动/停止不得误停别的实例。

## 4. 提交幂等与批次原子性

1. 将现有submission_id/idempotency key限定在workspace + user + 入口命名空间，绑定规范化有效输入hash和明确的对象/版本/平台模型/参数引用。同键同输入返回同一任务/批次，同键异输入409。
2. 重发先复核当前访问权，不因知道一个key泄漏他人任务；同团队不同人、不同团队同名key不能互相命中。
3. 任务、必要的子调用计划、幂等记录和额度预占在同一短事务建立。两个并发请求不能各建一份任务或各扣一份额度。
4. 批量、双遍分镜、语音等保留稳定子步骤身份。混入无权对象/旧epoch/非法模型或参数时整批拒绝，不留下jobs、private binding、配额或持久事件的半批状态。
5. 不自动为旧请求改用最新对象revision、最新模型版本或新Key。内容变化/负责人变化按既有P5和新提交规则处理，不能借幂等命中绕过权限。
6. 结果下载/素材登记按job/步骤/结果标识幂等。重复终态和finalizing重试不重复生成，也不登记多份同一结果。

## 5. 网络副作用与恢复

- 在发送之前持久化足以判断执行阶段的记录；收到provider_job_id尽早受控持久化，查询/取消继续使用原配置及凭证版本。
- 已有远端ID恢复只能先查询/归档，不换账号重投生成；Key轮换与吊销、Provider停用分别按P4语义处理。
- 上游支持幂等才能复用其有依据的幂等机制；不要假设某header被供应商接受。无支持且可能已受理、响应丢失/进程在提交窗口退出，转unknown/待核对，不能自动POST第二遍。
- “没有收到响应”不等于“未发送”。只有能证明尚未交付上游、或有可依赖的上游幂等约束时才可自动重试提交。无法证明的窗口允许保守阻塞，不要求不可能的exactly-once。
- 下载、格式检查、FFmpeg及数据库登记与生成步骤分开恢复；处理失败不重做已经受理的生成。
- 查询/下载的重试要有界、退避且遵守P4安全出站规则。429及timeout按所处阶段处理，不一律重新提交生成。
- 取消/完成并发定义一个可解释终态规则。远端不支持取消时说明本地停止不代表远端停止或免费，不虚报已成功取消上游。
- 幻场素材登记延用账号/租户/素材身份边界，用数据库唯一性和最小状态机协调多进程，已有remote id持久保存。登记副作用与后续视频生成分开，不仅靠线程锁。未知登记状态同样不能盲目制造重复远端资产。

## 6. 原子额度和资源上限（不是金额账单）

沿用已冻结产品规则，实现以下可由平台管理员配置的限制：
- 用户/团队排队上限。
- 用户/团队按text/image/video/audio分类的每日提交额度。
- 全局、供应商账号、团队、用户并发上限；FFmpeg有独立本地执行槽。
- 平台及供应商暂停新调用；最长排队寿命。

建立可核对的最小reservation/usage记录即可；不要求金融总账或支付系统。

1. 预占和建任务原子提交。只有一个名额时并发请求最多一个成功；失败事务不留下负数、半扣或悬空占用。
2. 双遍分镜两次真实文本生成、语音每句/批次、图片数量等的quota单位必须明确，按实际已规划的生成工作量记录，不能只按顶层job数。区分HTTP请求次数与quota单位；例如一次请求返回多张图片，不在报告里混称为多次HTTP。未知后续付费步骤执行前追加预占或暂停。
3. 日界线默认UTC，后台可配置时区；原配额日绑定接纳时刻，跨天不重新免费占额或移动历史记录。最长排队寿命可默认24h并允许配置，过期未发送项按规则释放原日预占。
4. 明确未送上游的取消/失败可以释放；已经发送、受理或未知状态不自动返还提交额度。人工调整带原因、操作者和关联任务证据，防止失败/取消刷量。
5. 本地Worker执行槽、远端可能仍运行的在途名额分别记录。Worker退出或本地取消不能把远端占用无条件清零；unknown名额保守保留，直到获得终态证据或获权管理员核对。
6. 各种预约/attempt/用户及团队计数使用一致锁顺序，避免一组路径先job后quota、另一组反向造成死锁。用真实PG竞争验证，不以进程内计数保证跨进程正确性。
7. 调度可用简单按团队轮转或等价方案，证明一个团队积压不会饿死另一个满足资源条件的团队。不要建复杂调度平台；用可重复的调度轨迹和有界轮次证明，不使用无依据的吞吐目标。

## 7. 权限、P4治理与P5结果保护

每个**新生成/新增付费子步骤**之前，重新检查当前账号是否有效、团队/作品成员关系、目标对象负责人/assignment epoch、模型/Provider启用状态、平台暂停和额度。检查基于当前数据库权限，不把已过期的浏览器Cookie当作后台永久凭证。

已提交的固定正文/参数不得随当前编辑静默替换。生成基于旧内容但仍可合法执行时，只保留候选；是否继续新步骤按明确规则判断，不能以恢复为由重绑新版本。

对于已经受理的远端任务，用狭义系统执行能力继续查询/下载/归档：只操作绑定任务和原scope，不产生新的创作调用，不给已经撤权的提交者重新授权。若凭证被吊销而无法查询，显示阻塞待核对，不换Key重投。

全部创作结果继续通过P5候选路径，Worker不会采纳、恢复或覆盖人工对象。明确采纳仍校验当前对象权限、revision、epoch和依赖，OVC-P5-01/02回归保持。导出仅登记素材，不取得对象编辑权。

P4的参数完整性、协议支持矩阵、凭证加密、版本绑定、吊销、新旧Key查询隔离、SSRF/重定向/认证隔离不放宽。新增attempt/unknown/审计/后台响应不得泄漏Key或密文。无真实付费API测试授权。

## 8. 最小后台及用户闭环

复用现有/admin与任务中心，不开发另一套后台：
- 平台管理员可以设置简单额度/并发/排队上限、暂停平台或Provider新调用，查看各队列、占用与用量。
- 任务显示本地/远端阶段、可恢复/待核对原因及允许操作；未知状态进入明确列表。
- 提供最小人工核对动作：按可信上游证据关联原handle或标记已确认终态/未受理，并更新对应占用；记录actor、原因及原状态，不能仅“清零未知任务”解除所有限制。
- 如需重新发起可能产生费用的任务，必须明确新提交及风险、重新授权/预占，不伪装成免费查询。测试仍只调用fake。
- 普通成员只能看到当前获权作品的任务及允许的使用信息；viewer不能生成，editor不能改平台额度/他人任务，团队owner不能配置平台Key。
- 新增路由纳入现有fail-closed ACL分类并提供HTTP正反例。后台页面连接真实接口，不能以按钮/截图代替业务行为。
