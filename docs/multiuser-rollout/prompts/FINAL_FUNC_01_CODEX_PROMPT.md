## 5. 一条代表性用户链路

采用一个小作品、同一集的镜头X/Y、一条共享时间线。两个普通editor使用独立Cookie上下文。后台准备可以自动化，下面的主要创作操作应在真实浏览器中完成：

1. 分工编辑。A修改自己对象X，B修改Y，通过现有保存路径提交。刷新或重新登录后，两份内容都保留；没有对象权限的一方保持只读或得到明确拒绝，不把禁用按钮当成服务端ACL证据。
2. 选择模型并生成。使用平台发布的本地fake模型，通过普通界面选择并提交代表性文本/媒体生成。至少覆盖一条文本和一种可见媒体结果，推荐已有文本及图片协议；不要因此要求接通所有视频/语音供应商。由实际独立Worker处理，不直接调用方法伪造任务终态。
3. 候选与审核。页面能够看到/比较候选，负责人通过实际操作明确采纳；生成成功不能自动替换人工正文。管理审核由有权M针对当前revision完成，不要求editor绕过审核权限。已有迟到候选/旧审核版本反例优先沿用测试，不机械再造整套竞争演练。
4. 剪辑。将A/B成果纳入同一短片，例如两个短画面及简短标题。明确指定一名时间线负责人并取得既有租约，另一方只读/等待；不新增同时共编。保存并刷新后，时间线内容与素材引用存在。
5. 真实导出。从现有界面发起导出，由单Worker运行真实FFmpeg，产出一个可读取、可解码的短MP4（建议约2–5秒，时长/分辨率采用已支持设置）。记录实际任务ID、素材ID、ffprobe时长/尺寸/流及解码或播放检查；不以只有文件名、HTTP200或静态截图证明导出成功。
6. 持久性。换到新会话或刷新后，原X/Y正文、采纳/审核版本、剪辑内容及导出入口可读取，用户仍按权限访问。

不评判fake生成的艺术质量；fake必须返回合法协议响应及真正可解码的媒体。记录明确提交的生成任务数及fake请求账本，区分submit、poll、download；不把每次轮询算一次生成，不要求所有场景固定为同一个数字。
