修复实际 `ObjectDrafts`、`CollaborationClient` 与宿主页之间的状态协调：保存成功响应晚于同对象较新远端快照时，不能只推进 drafts.base.revision，留下页面/rows/baseline 的旧正文，并用新版本号保存旧内容。

## 先保留确定性红测

复用已经取得的新增失败测试和原始日志，记录运行时 SHA、是否新增测试文件/工作区补丁。不要改写原始结果，不能把 mock CAS 声称为真实 HTTP 或浏览器。

红测要符合真实提交语义：
1. 用实际 CollaborationClient 和实际对象拆分/合成，不替换业务状态机。
2. 第一次请求按 CAS/epoch 验证成功并将服务端对象存为 r2，复制 r2 回执；只延迟这份响应交付。
3. 同一负责人另一客户端从 r2 合法更新为 r3，epoch 不变。可控 CAS transport 必须拒绝不匹配 revision；不能无条件接受写入。
4. 第一客户端仍在保存时收到实际 r3 数据，经真实 mergeRemoteRows 得到宿主文档，再释放旧 r2 回执。
5. 只修改 note（或当前对象的另一合法字段），继续实际保存。
6. 记录页面文档、client rows、baseline、draft base、请求 revision/content、服务端最终对象和保存状态。

缺陷基线会出现 expected_revision=3 配上未明确接受的旧 v2 正文，最终 r4 覆盖 v3。

## 最小实现选择

允许选择最小且可证明一致的方案，不要求两套都实现：

A. 没有保存期间新输入时，将已观察到的 r3 同时应用到宿主文档、rows、baseline 与 drafts，再将状态表示为已保存/已同步。
B. 旧回执后保留本地正文，将更新的 r3 留作冲突比较，禁止自动用 r3 为旧正文签发新保存票据；通过既有明确比较/放弃/重提流程处理。

存在保存期间的本地新增输入时，不能直接加载 r3 丢掉该草稿。修复必须保留已有“明确比较后重提”的能力；明确重提也必须再次受服务器 CAS 约束。

不要只修 ObjectDrafts 的孤立断言而让 host/client 状态继续错位。也不要通过以下手段换绿：屏蔽保存期间 SSE、固定延时、强制全页刷新、自动丢草稿、无条件忽略成功回执、自动拉最新 revision 重发旧全文、放宽后台 CAS。

## 最小必要回归

1. 核心 r2 已提交/响应延迟 → r3 远端先到 → 旧 r2 回执 → 仅改 note：不能静默覆盖 v3。若选择冲突策略，在明确处理前不得自动发送该写入。
2. 同样顺序，但保存期间又有本地文字输入：保留草稿及远端内容的比较信息，不误报全部已保存。
3. 只有本次 r2 回显、没有更新 r3：仍可正常完成保存，不制造永久冲突或网络回声写。
4. 常规顺序（r2 回执先到、r3 后到）仍正确；较旧读取不得替换已观察到的新版本。
5. 保存 X 同时接收独立 Y 更新：不抹掉 Y，不把 Y 当作自己修改重发。
6. 旧页面/旧作用域回执不得修改新作品；assignment epoch 改变仍按原权限与冲突规则拒绝。
7. 实际保存结果与宿主文档的传播必须验证。可以用现有宿主回调集成测试，或一条隔离真实浏览器窄流程；不要求重做原 61+17 整套浏览器。

mock CAS 对客户端顺序测试有效，不强制为了本前端缺陷另建数据库并发平台。若用真实 HTTP/浏览器补跑，要清楚区分服务端已经提交与客户端尚未收到回执，只延迟测试自身请求的交付，不在生产代码加调试后门。
